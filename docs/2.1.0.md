# Drivio 2.1.0

## Audit et plan

Base initiale : 2.0.3, Next.js 16 / Prisma 7, SQLite DEV et PostgreSQL PROD,
Kyros SSO v4. Les entretiens sont déjà modifiables ; les pleins et dépenses
n'ont qu'une création. Les coûts sont calculés à la lecture, les intervalles
carburant sont également persistés. Un plein est lié à une dépense unique et
éventuellement à un relevé, parfois saisi manuellement.

Ordre d'implémentation : taxonomie compatible, édition transactionnelle,
API Hub en lecture seule, thèmes et dashboard, validation locale.

Les types d'entretien restent stockés sous leur code historique pour préserver
les jauges et rapprochements. Le formulaire présente une famille puis un
sous-type. Les dépenses conservent leur catégorie et gagnent une sous-catégorie
facultative. Les nouvelles colonnes de classification des entretiens sont
remplies uniquement par correspondance certaine du code historique ; jamais
par déduction automatique du texte. Un ancien type générique (Freins, Filtres,
Pneus) gagne une catégorie mais garde une sous-catégorie vide. Un type inconnu
ou Personnalisé reste non classé. Les codes d'origine et intitulés sont conservés.

L'API Hub utilise un jeton personnel opaque, limité à la lecture des widgets,
créé depuis une session Kyros et révocable. Aucun contrat d'échange de jetons
Kyros/LUMA n'existe dans ce dépôt : le jeton Drivio doit être conservé côté
serveur par LUMA. Les cookies de session ne sont pas acceptés par cette API.

Migration additive `20261118100000_drivio_210` pour les deux moteurs :
catégorie/sous-catégorie d'entretien et d'échéance, sous-catégorie de dépense,
préférences visuelles, empreinte et expiration de l'accès Hub.
Ne pas l'appliquer à la production sans sauvegarde et autorisation.

## Classification des entretiens

La définition unique est `src/lib/taxonomy.ts`, les libellés sont dans
`src/lib/constants.ts`. Ajouter un sous-type implique sa définition, sa famille,
ses libellés et, si pertinent, une règle dans `maintenance-detection.ts`.

| Catégorie | Sous-catégories |
| --- | --- |
| Freinage | Plaquettes, disques, liquide de frein, étriers |
| Moteur | Vidange, bougies, distribution, refroidissement |
| Transmission | Boîte de vitesses, embrayage, huile de boîte |
| Échappement | Catalyseur, silencieux, ligne d'échappement |
| Carrosserie | Peinture, pare-chocs, réparation |
| Pneumatiques | Remplacement, équilibrage, géométrie |
| Filtres | Huile, air, habitacle, carburant |
| Suspension et direction | Suspension, direction |
| Électricité et visibilité | Batterie, essuie-glaces, éclairage |
| Révisions et contrôles | Entretien constructeur, contrôle technique |
| À classer / personnalisé | Aucune attribution automatique |

Chaque famille propose également « Non précisée ». Les dépenses ont un type
et un sous-type facultatif, validés ensemble côté serveur. Les interventions
et échéances conservent le champ `type` historique ; les nouvelles colonnes
`category` et `subcategory` sont dérivées côté serveur du choix explicite.
Les jauges rapprochent toujours les mêmes codes et références ; une famille
générique n'est jamais convertie arbitrairement en pièce précise.

La suggestion d'entretien fonctionne localement par mots-clés et synonymes,
insensibles à la casse, aux accents et à la ponctuation. Elle exige le clic
« Utiliser cette suggestion » et ne remplace pas une correction manuelle.
Plusieurs opérations reconnues produisent un message d'ambiguïté, sans choix
automatique. Un intitulé inconnu peut rester À classer. Aucun service IA externe.

## Édition et cohérence

- `PATCH /api/fuel/:id` réutilise le formulaire de création. Date, compteur,
  litres, montant, prix/L, plein complet, carburant et station sont modifiables.
  Le véhicule est fixé par l'enregistrement possédé, jamais par le corps reçu.
  Le prix/L doit correspondre au total et au volume (tolérance d'arrondi au
  millième et au centime) ; laisser le champ vide permet de le calculer.
- La mutation verrouille le véhicule, contrôle les voisins, met à jour la même
  écriture et sa dépense, puis recalcule tous les intervalles. Un relevé issu
  uniquement de ce plein peut être corrigé ; un relevé manuel ou partagé est
  conservé et le plein est associé à un autre relevé cohérent. Aucun doublon de
  plein ou de dépense n'est créé. Une contradiction annule la transaction.
- `PATCH /api/expenses/:id` conserve véhicule et relations. Une dépense liée à
  un plein renvoie vers l'édition du plein. Une dépense d'entretien conserve
  sa catégorie Entretien et synchronise coût, date et compteur de l'opération,
  sans modifier son intitulé. L'édition depuis Entretiens reste disponible.
- Les statistiques sont recalculées à la lecture ; les requêtes d'édition
  actualisent la page. Les dépenses d'assurance virtuelles se changent dans le
  contrat, pas en créant une fausse écriture.

## Dashboard et apparence

Le véhicule est sélectionné dans l'URL, contrôlé côté serveur. Les actions
courantes conservent sa sélection. Sur mobile, compteur et prochaine échéance
précèdent les analyses ; la photo reste sur le dashboard de bureau et dans le
Garage. Alertes, indicateurs utiles, prochains entretiens classés et coûts par
famille viennent avant les graphiques et les jauges détaillées.

Les totaux d'entretien regroupent les coûts effectivement renseignés ; une
famille sans coût reste indiquée « Coût non renseigné ». Les coûts d'usage
incluent les pleins une seule fois et les assurances selon les règles existantes.
Le graphique de distance conserve une projection visuellement distincte. Le
mois courant reste incomplet et les données insuffisantes sont indiquées.

Thème sombre par défaut, clair ou automatique ; palettes cuivre et ardoise.
Tous les composants utilisent les rôles CSS de `globals.css`. Les préférences
sont enregistrées sur le compte via `PATCH /api/preferences/theme`, et le rendu
serveur applique les attributs HTML avant l'affichage. Un cookie conserve le
dernier choix sur la connexion ; aucune injection tardive de thème n'est
nécessaire. Le mode automatique réagit aux préférences système via CSS.

## Mise à niveau (à effectuer dans l'environnement voulu)

1. Sauvegarder la base et les volumes de documents/photos.
2. Installer les dépendances du lockfile avec Node 24 et générer le client
   correspondant au moteur : `npm run db:generate` pour SQLite ou
   `npm run db:generate:postgres` pour PostgreSQL.
3. Appliquer les migrations Prisma, une seule fois par base : `npm run db:deploy`
   ou `npm run db:migrate:postgres:safe` pour PostgreSQL. Ne pas utiliser `db push`
   comme remplacement des migrations.
4. Construire (`npm run build`) puis redémarrer l'application. Migration avant
   nouveau code : les requêtes lisent les nouvelles colonnes.
5. Vérifier une session Kyros, les compteurs, un entretien, les dépenses et les
   préférences. Créer ensuite un accès Hub si nécessaire.

Une réexécution de `migrate deploy` est suivie par Prisma ; ne pas rejouer le SQL
brut sur une base déjà migrée. Aucun script de suppression ou de reclassement
par heuristique n'est nécessaire. Un retour à l'ancien code peut conserver les
colonnes ajoutées ; ne pas supprimer les nouvelles données lors d'un rollback.

## Limites de validation

Pas de déploiement, migration de production, test physique mobile, test de
technologie d'assistance, flux Kyros réel ou consommateur LUMA réel. LUMA reste
à raccorder côté serveur au contrat documenté dans [API-HUB-LUMA.md](API-HUB-LUMA.md).
Les comptes et observations de la recette navigateur sont synthétiques.
Les mises à jour de dépendances sont limitées aux versions majeures existantes,
et `npm audit --omit=dev` est passé à **0 vulnérabilité** après mises à jour
ciblées Next 16.4.6, Zod 4.6.7, fast-uri/source-map-js et override mysql2
3.24.6 (dépendance transitive épinglée par Prisma). Aucun changement majeur.
L'audit complet incluant les outils DEV conserve des alertes ; le résultat
zéro concerne uniquement `--omit=dev`, pas l'ensemble de l'outillage.
